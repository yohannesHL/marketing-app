# Meta Ads customer connection

Issue [#5](https://github.com/yohannesHL/marketing-app/issues/5) connects a customer's Meta user authorization to discovered ad accounts. The server owns the OAuth configuration, exchanges and verifies tokens, and registers account metadata. Customers select discovered destinations explicitly. Session, ownership, encrypted persistence and revocation/deletion receipt handling use the shared connection foundation.

## Meta app configuration

1. Create a **Business** app in the Meta App Dashboard and add **Facebook Login for Business** and the Marketing API use case/product.
2. In Facebook Login for Business → Configurations, create an **Ads-specific User access token configuration**, select the required assets, and include `ads_management`, `pages_read_engagement`, and `pages_show_list`. The current permission reference lists the latter two as dependencies of `ads_management`. Copy its configuration ID. `ads_management` supports both reading and managing ads; add `ads_read` to an independently designed reporting configuration when needed. `business_management` is needed only when implementing business-management endpoints.
3. Register the exact HTTPS callback URI used by the server. Protocol, hostname, port, path and trailing slash must match; the code exchange reuses that same URI. Configure app domains, privacy policy, deletion instructions/callback and deauthorization callback in the dashboard. Enable strict redirect matching.
4. Before serving customers who have no role on the app, obtain permission **Advanced Access** through App Review. Facebook Login for Business explicitly also requires Advanced Access to `public_profile` for external-user authorization. Complete Business Verification and any required dashboard review obligations. Prepare a screencast showing login, consent, account discovery and the requested functionality.
5. Check **Marketing API Access Tier** separately: its current labels are Limited Access and Full Access. Full Access has a documented qualifying threshold of 500 Marketing API calls over 15 days; the dashboard is authoritative for app eligibility. Permission approval, verification and access tier do not assign customers a role on any account.

Sources: [Facebook Login for Business](https://developers.facebook.com/docs/facebook-login/facebook-login-for-business/), [permissions and dependencies](https://developers.facebook.com/docs/permissions/), [Marketing authorization](https://developers.facebook.com/docs/marketing-api/overview/authorization/), [login security](https://developers.facebook.com/docs/facebook-login/security/).

## Runtime and authenticated routes

`CONNECTION_MODE=mock` requires `META_ADS_MOCKOON_URL` pointing to the explicitly permitted loopback fixture. Mock mode uses synthetic app/configuration IDs and a fixture secret; it needs no Meta customer credentials. `CONNECTION_MODE=live` requires server secrets/settings `META_APP_ID`, `META_APP_SECRET`, and the Ads-specific `META_LOGIN_CONFIG_ID`. Optional `META_GRAPH_VERSION` and `META_MARKETING_VERSION` default to v26. Neither mock IDs nor a loopback host are used as a fallback in live mode. Each grant records MOCK or LIVE, and reconnect/read/discovery/selection reject a different current mode before provider use. A fresh OAuth start also cannot overwrite an existing same-subject grant in another mode.

The current delivery has fixture evidence only: the user chose mock validation, and external app approval/customer access has not been validated live. Keep `CONNECTION_MODE=mock` for this delivery. Live platform evidence and any enabled live campaign workflow require their separate review and rollout work.

| Route | Input and behavior |
| --- | --- |
| `POST /api/connections/meta/start` | Signed-in session, exact Origin, JSON `{}` or owned `authorizationId` for reconnect; returns consent URL and mode. |
| `GET /api/connections/meta/callback` | Same signed-in session, state and provider code/error; verifies provider identity, discovers accounts before persisting the grant, then atomically consumes state and synchronizes the returned credential version. |
| `POST /api/connections/meta/:id/refresh` | Signed-in owner, exact Origin, JSON `{}`; repeats discovery, not token refresh. Expired Meta authorization requires reconnect. |
| `POST /api/connections/meta/:id/check` | Signed-in owner, exact Origin, only `destinationId`; reads the owned discovered account and reports read/write capability. |
| `POST /api/connections/meta/:id/select` | Signed-in owner, exact Origin, only `destinationId`; rechecks provider account tasks and uses version-bound stored ALLOWED metadata before selection. Reporting-only accounts remain readable but cannot select for campaign management. |
| `POST /api/connections/meta/deauthorize` | Public bounded form callback; verified signature then persistent lifecycle receiver. No browser session/Origin requirement. |
| `POST /api/connections/meta/data-deletion` | Public bounded form callback; verified signature then deletion receiver and receipt response. |
| `GET /api/connections/meta/deletion-status/:receipt` | Public opaque alphanumeric receipt; returns only its status, never identity or provider data. |

All JSON responses are no-store. OAuth callbacks requested as HTML redirect only to the configured origin's `/connections` page with fixed provider/result query values; codes, tokens and provider error descriptions never enter the redirect. JSON callbacks return safe structured errors. Bodies cannot supply tokens, provider account IDs, granted scopes, callback URLs, user IDs or capability overrides.

## Server client and integration contract

`MetaAdsClient` takes `appId`, `appSecret`, `configId`, and `redirectUri`; optional `graphVersion` and `marketingVersion` default to `v26.0`. App secrets are server secrets. Never use a `NEXT_PUBLIC_` variable for them. Supply configuration from trusted deployment settings, never request parameters.

The live client fixes its hosts to `www.facebook.com` for authorization and `graph.facebook.com` for API calls. There is no production custom-host option. `testBaseUrl` is a deliberate HTTP loopback-only fixture override; it must not be set by production configuration or customer input. Requests reject redirects, use a ten-second timeout, and produce fixed, structured errors without reflecting provider error messages, OAuth codes or tokens. Requests with access tokens use bearer authorization and server-generated `appsecret_proof`. No automatic retries are performed.

| Method/property | Contract |
| --- | --- |
| `scopes`, `pkce`, `redirectUri` | Server-defined requested permissions, `pkce=false`, exact callback. Use these with the foundation's OAuth request. |
| `authorizationUrl(state)` | Business Login URL with `config_id`, `response_type=code`, original state and callback. No ad-hoc scope or PKCE parameter. |
| `exchangeCode(code, expectedProviderUserId?)` | Server code exchange, then long-lived exchange, token verification and `/me` identity verification. Returns a `ProviderGrant`-compatible verified grant plus display name, token type and data-access expiry. |
| `verifyToken(token, options?)` | Checks debug token app ID, validity, USER type, numeric subject, required actual scopes and expiry, then checks `/me` matches the same subject. Optional expected subject binds a reconnect to the existing identity. |
| `discoverAccounts(token)` | Retrieves all account pages, including empty/short pages with a next link; returns metadata and `canManage` capability. |
| `readAccount(token, externalId)` | Rechecks the selected account's ID, current account status and user tasks. |
| `validatePausedCampaign` | Uses provider `validate_only` without creating an object. |
| `createPausedCampaign` | Creates only a PAUSED campaign, with explicitly supplied special categories and no campaign budget. Returns its ID. |
| `readCampaign`, `removeCampaign` | Verify the expected owning account; cleanup additionally requires PAUSED, then deletes only the supplied campaign ID. |

An OAuth callback first claims the session-bound exchange through `CustomerConnections.claimOAuthExchange`, calls the trusted provider client, and passes the verified grant and claim token to `completeAuthorization`. The claim occurs before the error/cancellation handler: a losing duplicate callback cannot cancel the winning exchange. Completion and cancellation require that same claim token. Never expose an endpoint that accepts user-supplied access tokens or verified scopes. Save credentials only through the encrypted foundation. Grant `externalGrantId` is the verified app-scoped Meta user ID; a signed removal callback can therefore invalidate all capability records associated with that app/user grant. Local disconnect is capability-specific.

This uses a **User** configuration because `/me` must identify the human customer and `/me/adaccounts` must enumerate their accessible accounts. A Business Integration System User token is a different integration model: explicitly delegated business assets, client business portfolio identity, web-only onboarding and potentially no time expiry. It must not be silently accepted by this adapter.

The Business Login documentation does not verify combining its `config_id` flow with PKCE. Meta separately documents a testing OIDC flow using `openid`, nonce and PKCE; this implementation deliberately does not assume those parameters work with Business Login. [Business Login](https://developers.facebook.com/docs/facebook-login/facebook-login-for-business/), [manual code exchange and token inspection](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/), [testing OIDC/PKCE flow](https://developers.facebook.com/docs/facebook-login/guides/advanced/oidc-token/).

## Token and account lifecycle

Short-lived User tokens normally last 1–2 hours and long-lived tokens approximately 60 days, but these are estimates. The client uses the earliest actual expiry supplied by the token exchange, token debug response or data-access expiry. A documented zero token expiry is represented as `null`; an expired/invalid token fails closed. Provider error 190 requires reconnection. There is no Facebook refresh token and this adapter exposes no generic refresh method. Users must reconnect when authorization becomes invalid. [Access tokens](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/), [long-lived exchange](https://developers.facebook.com/docs/facebook-login/guides/access-tokens/get-long-lived/).

Account discovery asks for `id`, `account_id`, `name`, `account_status`, `currency`, `timezone_name`, and `user_tasks`. `externalId` is the numeric account ID; `graphId` is `act_` plus that ID. The client exposes inactive and reporting-only accounts as metadata with `canManage=false`. It requires current `account_status=1` and `ADVERTISE` or `MANAGE` task to create/validate a campaign. `ANALYZE` alone allows reporting rather than writes. Fresh checks and selection revalidation persist account metadata using the original credential version, including role/status denials; a denied/unavailable account is deselected and its pending local work is cancelled. App permission approval and customer account permissions remain separate requirements. Current `user_tasks` replaces assumptions about legacy numeric `user_role`. [Account fields](https://developers.facebook.com/docs/marketing-api/reference/ad-account/), [assigned-user task mapping](https://developers.facebook.com/docs/marketing-api/reference/ad-account/assigned_users/).

Discovery follows pagination until `paging.next` is absent, even after an empty/short page. The next URL must retain the configured trusted origin and exact account edge; only its `after` cursor is reused. Provider-supplied tokens and other query parameters are never forwarded. Repeated cursors and more than 100 pages fail rather than silently returning a partial result. Cursors are not persisted. [Graph pagination](https://developers.facebook.com/docs/graph-api/results/), [Meta's account enumeration SDK](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/user.py).

Campaign helper calls must also pass the shared operation gate and the customer's explicit account selection. They support future issue #6/#7 verification: always `status=PAUSED`, `special_ad_categories=[]` when no category applies, and `is_adset_budget_sharing_enabled=0`. No helper activates campaigns, creates ads/ad sets, or supplies a spending budget. `validate_only` is a server API call but does not mutate; successful validation returns `success:true`. Creation returns an ID; read it back and verify account/status before considering creation confirmed. Cleanup deletes that saved object alone, never the bulk account campaign edge. These helpers are not a route authorization boundary. [Creation/validation](https://developers.facebook.com/docs/marketing-api/reference/ad-account/campaigns/), [campaign read/deletion](https://developers.facebook.com/docs/marketing-api/reference/ad-campaign-group/).

## Signed callbacks

`verifyMetaSignedRequest(signed_request, appSecret)` returns verified `userId` and optional `issuedAt`/`expiresAt`. It requires exactly two canonical base64url segments, HMAC-SHA256 over the **original encoded payload segment**, constant-time equal-length signature comparison, expected algorithm, numeric app-scoped user ID and valid optional timestamp types. Invalid signatures or payloads cause no persistence changes. It does not impose an undocumented five-minute cutoff, so authenticated older callbacks/retries remain processable.

The callback HTTP layer receives form POSTs and verifies them before acting. It delegates only the verified subject, a hash of the original signed request as `eventId`, and verified `issued_at` in Unix seconds. No raw signed payload is persisted by the route. The persistent receiver can deduplicate events and fence pending OAuth attempts, preventing replayed older callbacks from removing a later reconsent. Deauthorization removes usable credentials and stops future local work for every record matching the verified app-scoped identity within the configured connection mode. Current manual-login docs confirm dashboard deauthorization callback delivery but do not specify a complete current response schema; an HTTP 200 acknowledgment is the implementation contract, and must be verified with the app's dashboard integration test before live rollout. Lifecycle dispatch does not initialize the outbound Meta HTTP client, so receipt/removal processing does not depend on an available discovery endpoint. Missing lifecycle persistence fails closed with 503 rather than claiming success.

Data deletion has a documented additional response contract: initiate deletion of Facebook-derived data, persist an opaque alphanumeric receipt and return `{"url":"https://your-app/deletion/status/receipt","confirmation_code":"receipt"}`. The public HTTPS URL gives a human-readable truthful status; it does not expose tokens or raw user IDs. It must reflect deletion work actually completed or pending. Retained audit/operational data must match the application's published privacy policy. Unknown subject requests and repeats should complete safely. `MetaLifecycleStore` owns this persistence and receipt lifecycle; the signature helper only establishes authenticity. [Deletion callback and signature example](https://developers.facebook.com/docs/development/create-an-app/app-dashboard/data-deletion-callback/), [manual login/deauthorization](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/).

The implemented lifecycle store erases known Meta authorizations, destinations, local operations/audits and execution invocations linked by verified authorization ID and connection mode. Mixed executions retain independent Google/other-grant invocations; their aggregate request/results remove only identified Meta data and mark `providerDataRemoved`. It does not guess which unlinked legacy records belong to a Facebook subject. Before approving a public/live rollout, audit and remediate any historical Meta-derived rows lacking this verified provenance, including old invocation payloads and backups, and align retained receipt/event/fence records with the privacy policy. Fixture validation establishes deletion of known linked data; it does not prove a production legacy dataset has been remediated.

## Ads and Social separation

The Ads configuration is separate from future Social configurations. Do not automatically add publishing permissions to Ads grants or reuse an Ads token as a Social connection. Facebook publishing needs a selected Page, a Page token, `CREATE_CONTENT` task and `pages_manage_posts` with its Page dependencies. Instagram with Facebook Login uses a professional account linked to a Page and `instagram_basic`/`instagram_content_publish`; Instagram Login instead uses Instagram-specific credentials, `instagram_business_basic`/`instagram_business_content_publish`, an Instagram User token and `graph.instagram.com`. Those independent login and publishing contracts belong to issue #13. [Facebook Reels](https://developers.facebook.com/docs/video-api/guides/reels-publishing/), [Instagram publishing by login model](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/content-publishing/).

## Implemented application and owner settings

Apply all migrations and generate Prisma. Configure the foundation's `APP_ORIGIN`, database and vault keys. Local mode: `CONNECTION_MODE=mock`, `META_ADS_MOCKOON_URL=http://127.0.0.1:3911` and `npm run mock:meta`. Live mode: `CONNECTION_MODE=live`, `META_APP_ID`, `META_APP_SECRET` and the USER-token `META_LOGIN_CONFIG_ID`; register exactly `${APP_ORIGIN}/api/connections/meta/callback`. Versions default to v26.0 through `META_GRAPH_VERSION` and `META_MARKETING_VERSION`. Mock mode uses synthetic credentials and cannot replace or revoke a live grant.

| Endpoint | Method/body | Behavior |
| --- | --- | --- |
| `/api/connections/meta/start` | POST `{authorizationId?: string}` | New consent or owned reconnect |
| `/api/connections/meta/callback` | GET code/state | Atomically claim callback work; verify USER identity/permissions; persist encrypted grant and accounts |
| `/api/connections/meta/{id}/refresh` | POST `{}` | Rediscover accounts; expired user tokens require reconnect rather than pretend refresh |
| `/api/connections/meta/{id}/select` | POST `{destinationId}` | Recheck current account status/tasks before selection |
| `/api/connections/meta/{id}/check` | POST `{destinationId}` | Read-only account check; management readiness remains separate |
| `/api/connections/meta/deauthorize` | POST form `signed_request` | Verify application signature; revoke relevant Ads and Social grants |
| `/api/connections/meta/data-deletion` | POST form `signed_request` | Remove known Facebook-derived connection data and return a real confirmation receipt |
| `/api/connections/meta/deletion-status/{receipt}` | GET | Public opaque receipt; human HTML or JSON status without identity/credentials |

Register the two signed callback URLs in Meta's dashboard. Unlike customer mutations, these authenticated provider callbacks do not require a customer cookie or application Origin. They remain processable when outbound OAuth is unavailable. Signature verification uses the original encoded payload and constant-time comparison. Callback event digests make retries idempotent; revocation fences are checked inside the OAuth completion transaction, including pending consent without an existing grant. Second-resolution provider timestamps cover that complete second, preventing fractional local times from bypassing revocation. Later consent is preserved against old callback replay.

Deletion removes the verified subject's matching grants, destinations, operations and connection metadata/audit records, plus explicitly linked provider invocations/results. Mixed executions retain unrelated Google or other-grant history. Minimal one-way subject/event digests and opaque confirmation/status records remain to prevent replay and evidence request processing; no plaintext Facebook subject/token is retained in those receipts. Customer login and independent provider data remain. Backups and legacy imports with unknown Facebook-app provenance require the operator's retention/cleanup process; resolve that provenance and cleanup before production approval. Historical simulated/unknown-source records must never be misrepresented as verified Facebook data or silently mapped to a different grant. New real execution must populate invocation authorization/destination/mode linkage.

Run `npx tsx --test tests/integration/meta-ads-provider.test.ts tests/integration/meta-connections.test.ts tests/integration/meta-lifecycle-timing.test.ts`. Actual Facebook consent, App Review, callback compatibility and live account/campaign access remain unvalidated; this release is tested with Mockoon as requested. An Ads grant does not authorize Page/Instagram publication.
