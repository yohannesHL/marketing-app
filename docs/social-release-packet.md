## Deployment and secure customer access

Have the operator prepare the deployment with writes still disabled:

1. Use Node 24.16.0 or a later Node 24 release, as required by the package engines. Apply every checked-in migration to the intended durable database. Stop traffic and continuous workers for an existing-database maintenance window, take an access-controlled consistent backup, retain its required keys and use a reviewed migration baseline. Local SQLite web/worker processes must use the same absolute `DATABASE_URL=file:/...` and run on the same host and persistent local volume; a relative URL can resolve differently from their different working directories. The adapter retains the existing journal mode, applies a finite per-connection wait and acquires write intent before local transaction callbacks; it never replays provider requests. Use SQLite's consistent backup mechanism or stop every database user before taking a verified consistent file backup. Copying only a running database's main file can omit committed data when a journal is active. Do not reset or replace customer data to reproduce a test result. Generate the Prisma client and deploy migrations using the commands in [customer security](customer-connection-foundation.md) and follow [storage operations](social-delivery.md).
2. Install server-only `CONNECTION_TOKEN_KEYS` and `CONNECTION_ACTIVE_KEY_ID` in the secret store. The keyring uses named canonical-base64 32-byte encryption keys. Keep old keys for rotation and retained backups. The database, decryption keys and private media volume must be restorable together.
3. Install FFmpeg/ffprobe. Set an absolute persistent `SOCIAL_MEDIA_DIRECTORY`, fixed provider-reachable HTTPS `SOCIAL_MEDIA_PUBLIC_ORIGIN` and a separate canonical-base64 32-byte `SOCIAL_MEDIA_SIGNING_KEY`. Every web/worker instance must share the database and private media. Keep files outside the public web root. Optional bounds are `SOCIAL_MEDIA_MAX_BYTES` and `SOCIAL_FFPROBE_PATH`.
4. Set the exact `APP_ORIGIN` and explicit `CONNECTION_MODE`. Mock mode uses only the documented loopback `*_MOCKOON_URL` settings; live mode uses real configured endpoints and cannot fall back to mock success. Keep `SOCIAL_PUBLISHING_ENABLED=false` and `SOCIAL_APPROVED_PROVIDERS=[]` during connection review. Do not change advertising settings as part of enabling Social.
5. Provision the pilot customer through the trusted `npm --workspace @launchpad/web run security:customer` command, with JSON supplied on standard input from a secure credential source. It outputs only `customerId`; never place the password in a command argument or evidence. An existing customer's authenticated `GET /api/auth/session` also returns that customer's ID. These are the supported ways to obtain the owner ID for X policy; do not dump credential tables or invent an identity from an email/username.
6. Build and start the web app; run `npm run social:worker -- run` under a supervisor with the same database, mode, keyring and media configuration. A scheduled job uses its checked database owner/grant and does not depend on an open browser session. Confirm restart, backup/restore and operational monitoring before the pilot. Logs and evidence must contain sanitized statuses only.

Exact allowlist entries are `GOOGLE:YOUTUBE_CHANNEL`, `META:FACEBOOK_PAGE`, `META:INSTAGRAM_PROFILE`, `TIKTOK:TIKTOK_PROFILE`, `LINKEDIN:LINKEDIN_MEMBER`, `LINKEDIN:LINKEDIN_ORGANIZATION` and `X:X_PROFILE`. Enable only the intended approved entries after the separate customer content review and owner pilot gates. A switch cannot create missing SDK support, permissions or provider approval.

## X spending visibility

X can charge for identity reads, media requests, post creation and outcome checks. Before enabling its workflow, verify every configured operation rate against the owner console; unknown media pricing must remain unconfigured rather than silently becoming zero. Bind each `X_API_OWNER_BUDGETS` entry to the securely obtained customer ID and explicit mode, with daily/delivery limits and operation ceilings. Set the provider's console spending cap as well.

The connection UI requires a separate explicit cost approval for connect/reconnect and fresh checks. Cached profile selection makes no new provider request. The composer quote is local: it uses owned inspected media and current configured rates, makes no X request and reserves no spending. The reviewed publication ceiling is immutable for that revision.

The ledger records **conservative allocations, not the actual bill or current provider credit balance**. It counts each authorized HTTP boundary, including renewal identity reads; retries, restarts and a new UTC day do not reset the lifetime delivery ceiling. Failed/revoked sends do not refund a reservation. UTC daily ceilings are separate from delivery ceilings and X console limits. Provider read deduplication is a soft guarantee, so the estimate must not promise discounted or free repeated reads. Credit exhaustion requires owner attention; it is distinct from a temporary rate limit. Preserve the ledger during recovery.

## Stop, recover, rotate and clean up

To stop new sends, first stop every continuous worker that can send to the affected provider. Then set `SOCIAL_PUBLISHING_ENABLED=false` or remove the affected allowlist entry, and reload/restart the web and worker instances with the disabled configuration. Workers capture configuration at startup; changing a secret-store value alone does not stop an existing process. Cancellation, edits, deselection, disconnect and revocation fence unsent jobs. A request already accepted by a provider may still complete; retain its saved progress and truthful uncertain/confirmed result. Do not delete a job or its receipts to make an unresolved send look cancelled.

Successful destinations are not resent during partial recovery. Bounded safe retries can resume saved preparation; an ambiguous publication needs status reconciliation before another send is permitted. To check a named uncertain delivery after stopping the continuous worker, keep web publication disabled and run a separate controlled `npm run social:worker -- reconcile-once <delivery-id>` process with publication enabled and only the affected provider kind allowlisted. Disable that temporary CLI configuration afterward; do not run the continuous worker loop with it. This status-only command remains available after automatic polling is exhausted; provider cooldowns, current authorization and immutable budget gates still apply. A status check cannot publish a replacement. If an X delivery has exhausted its reviewed cap, investigate the known receipt outside the app; increasing a new review’s cap does not override the old delivery’s cap. Processing failure retains its provider evidence; choose corrected media and a newly reviewed revision when required.

YouTube uses verified offline renewal. TikTok and X use a durable rotating-refresh lease; an uncertain exchange requires reconnect rather than reuse of a possibly consumed token. LinkedIn renewal requires approved MDP access and an actual unexpired refresh deadline. Meta USER access requires reconnect, not an invented refresh token. Known expiry, current permissions and the execution window remain enforced; an unknown refresh lifetime is never replaced with a fabricated duration.

For encryption rotation, install the combined new-and-old keyring and select the new active ID, then reload/restart every web and worker instance so all can decrypt both keys **before** rewriting any ciphertext. Only then run `npm --workspace @launchpad/web run security:rotate-keys`. Check the sanitized credential, social-progress and Meta Page-token counts; keep required old keys until unavailable records are resolved and retained backups no longer require them. Re-run a maintenance pass for concurrent updates. Rotate the separate media signing secret through an owner-approved maintenance plan that accounts for outstanding provider fetches; encryption rotation does not rotate that signing key.

Local cancellation is not provider cleanup. Use only the known owned receipt, current authorization and separately approved cleanup action, then confirm the actual provider outcome. TikTok's download cancellation is best effort and is not published-post deletion. Use the provider UI or a reviewed supported cleanup operation when necessary. Record the content's absence/removal at the provider, not merely disappearance from the local calendar.
