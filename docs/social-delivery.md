# Social delivery foundation

Social posts are separate from paid campaigns. Existing campaigns migrate to `PAID_ADVERTISING`; social posts use `SOCIAL_PUBLISHING`. A social destination requires an owned, selected `SOCIAL` authorization. Advertising access never authorizes publication.

The implementation supplies durable records, authenticated APIs, trusted media and provider adapters for the first release. The registry adds only separately configured providers; missing SDK/configuration or required permissions remain unavailable, and a switch cannot manufacture successful publication. See the [release packet](social-release-packet.md) for current merge/QA status and owner gates. Mockoon fixtures and protocol tests are development evidence; actual platform reviews and live pilots are tracked in [social publishing readiness](social-publishing-readiness.md).

## Owner and deployment setup

1. Install the customer/session configuration and server keyring described in [customer connections](customer-connection-foundation.md). Apply every Prisma migration before starting the web application or worker. Use a shared durable database rather than a worker-specific copy. For a local SQLite file, set the same absolute `DATABASE_URL=file:/...` for web and workers and colocate them on the same host with a persistent local volume; relative paths can resolve to different files from their different working directories. Run Node 24.16.0 or a later Node 24 release. Persistent local files use explicitly owned built-in SQLite connections while the Prisma/libSQL mapping remains in place; remote and in-memory clients retain their existing driver. The shared adapter retains the existing journal mode and configures each physical connection with a finite 100 ms busy timeout. Local transaction callbacks acquire write intent before reading. A rejected BEGIN can retry before the callback starts. A COMMIT can retry only when SQLite reports exact BUSY code 5 and confirms the same transaction remains active and uncommitted; four attempts yield between waits without repeating its statements. Exhaustion or any other commit error disposes the transaction and preserves the original error. Finished transactions release their physical connection even if Prisma retains their JavaScript objects. Callbacks, statements and provider requests are never replayed. [SQLite transaction rules](https://www.sqlite.org/lang_transaction.html#implicit_versus_explicit_transactions). A rejected BEGIN discards its physical connection before another attempt. Stop traffic and continuous workers for storage maintenance. Use SQLite's consistent backup mechanism, or stop all database users before taking a verified consistent file backup; copying only a running database's main file can omit committed data when a journal is active. Preserve the required keys and media with the backup. [SQLite backup](https://www.sqlite.org/backup.html).
2. Install FFmpeg, including `ffprobe`, on the web host. Set `SOCIAL_FFPROBE_PATH` if the executable is not on PATH. The server verifies media from its actual bytes and stream metadata, including display rotation; browser-supplied type, dimensions and duration are not trusted. See the official [ffprobe reference](https://ffmpeg.org/ffprobe.html) and [MP4 format options](https://ffmpeg.org/ffmpeg-formats.html#mov_002fmp4_002f3gp).
3. Mount a persistent private volume and set the absolute `SOCIAL_MEDIA_DIRECTORY`. All web and worker instances must see the same stored media. Keep this directory outside the public web root and restrict access to the service account. Uploads are capped at 64 MiB by default; `SOCIAL_MEDIA_MAX_BYTES` can set a cap up to 512 MiB. Each platform also enforces its own limits.
4. Set `SOCIAL_MEDIA_PUBLIC_ORIGIN` to the fixed HTTPS application origin reachable by providers and install a separate random 32-byte canonical-base64 `SOCIAL_MEDIA_SIGNING_KEY` in the secret store. Explicit mock mode permits loopback HTTP. The origin must serve `/api/social/media/:id/content`; provider links are signed, short-lived, scoped to the asset and verified against its current stored digest. TikTok additionally requires verified ownership of the chosen media domain or prefix. Never publish a private storage directory.
5. Keep `SOCIAL_PUBLISHING_ENABLED=false` and `SOCIAL_APPROVED_PROVIDERS=[]` until the relevant implementation and rollout evidence are reviewed. The allowlist uses exact destination-type values such as `GOOGLE:YOUTUBE_CHANNEL`, `META:FACEBOOK_PAGE` and `META:INSTAGRAM_PROFILE`. These switches authorize the application to run a provider; they do not confer platform approval or customer consent. `CONNECTION_MODE` must be explicitly `mock` or `live`.
6. Run `npm run social:worker -- run` under a process supervisor with the same database, mode, keyring and media configuration as the web application. `run-once` processes at most one eligible delivery; `reconcile-once <delivery-id>` checks one uncertain outcome. The loop polls idle work once per second and stops taking new work after a termination signal. A failed process must be restarted by the supervisor. Worker output contains sanitized status only. Workers capture their configuration and keyring at startup. To stop affected sends, stop those continuous workers first, change the write switch/allowlist, then reload/restart web and worker instances with the disabled configuration. Changing an environment or secret-store value alone does not alter a running worker.

## Review, scheduling and recovery

Saving content creates an immutable revision with explicit destination variants and publication controls. Approval binds that revision to the chosen destination list. Enqueue uses a customer-scoped idempotency key and rejects reuse with different content or scheduling instructions. Editing creates another revision, invalidates approval and supersedes work that has not been sent. The schedule stores an explicit UTC instant together with the customer's IANA time zone; ambiguous local times must be resolved in the UI before submission.

Workers claim jobs transactionally with leases and compare-and-set checks. They recheck the current revision, consent, destination ownership, selected status, mode, permissions, grant generation and media availability before every external call. Upload sessions, provider-side preparation IDs and other private progress are encrypted under the server keyring. Public APIs return only reviewed content and sanitized per-destination results.

A recorded successful destination is never resent during a partial retry. Safe, explicitly classified transient failures have bounded attempts and backoff. An interrupted publication becomes `UNCERTAIN`; status reconciliation must establish the result before another send is allowed. The publication marker remains durable across processing polls and worker restarts. No exactly-once guarantee is inferred from an HTTP timeout.

Automatic status polling is bounded. An operator can continue checking a named uncertain delivery with `reconcile-once` after that polling budget is exhausted. Stop the continuous worker, keep web publication disabled, and use a separate controlled CLI process with publication enabled and only the affected provider kind allowlisted. Disable that temporary configuration afterward; never run the continuous loop with it. Provider cooldowns, current authorization, lease checks and the delivery’s immutable API budget still apply, and status checks cannot submit a new publication. An exhausted X cap requires investigation of the known receipt outside the app; a higher cap on a new review does not override the old delivery. If stored access expires within the scheduled 60-second execution window, scheduling requires a renewable registration and stored refresh credentials. A known refresh deadline must also cover that window. YouTube supports verified offline renewal; TikTok and X serialize rotating refresh under a durable lease. LinkedIn renewal requires approved MDP access and an actual unexpired refresh deadline. Meta requires reconnection. Unknown refresh lifetimes remain unknown; the worker verifies actual same-subject scopes/expiry before execution instead of inventing a TTL. An ambiguous rotating exchange requires reconnect rather than blind reuse of the old token.

Cancel, reconnect, disconnect and signed provider revocation stop pending local deliveries. A provider request already sent cannot be withdrawn locally: the delivery retains its uncertain or confirmed result and cancellation request. Editing cannot make an older unresolved send disappear. Completed publication IDs remain visible. Platform adapters must implement any provider-side scheduling cancellation they introduce; this foundation does not silently claim to delete published content.

For key rotation, install the combined old-and-new keyring, select the new active key, and reload/restart every web and worker instance so each can decrypt both keys before ciphertext changes. Then run the existing customer security `rotate-keys` command. It now rotates both connection credentials and encrypted social upload progress using version checks. Retain old keys until `unavailable` is zero and rotation has completed; a concurrently updated progress record wins and can be covered by another maintenance pass. The command reports counts without tokens, upload session URLs or progress contents.

## Verification boundary

Integration tests use fresh temporary SQLite databases. They cover concurrent claims, duplicate enqueue, interrupted upload and publication, processing after publication, timezone changes, cross-customer records, expired media, secret redaction, revocation and key rotation. Media tests use actual PNG and FFmpeg-generated MP4 files and exercise signed links, byte ranges, tampering, expiry and deletion. These checks do not establish provider access, public approval or a real customer pilot.
